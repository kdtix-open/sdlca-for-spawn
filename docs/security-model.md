# Security model

This page is for someone deciding whether to trust and run the SDLCA agent kit. It says in plain words who can make the kit do work, what the agent can do once it is running, what the kit does to protect your tokens and other people's chat text, and which risks remain. It was checked against the kit's code on 2026-11-17, and its parts about the git address, `sdlca-look` and the Claude Code option on 2026-11-18. Read it before you choose anything beyond the read-only agent command.

The kit is an unofficial community project. It is not made, reviewed or supported by Spawn. We are a small project and have not had an outside security audit. Everything here is what we know and what we have tested, and the risks we cannot remove are listed without softening.

## The short version

- **The kit decides who may start work and where the agent starts. It does not decide what the agent does.** Your agent command decides that, and you choose it.
- **Only the account's owner, and people you list, can start work.** Everyone else is ignored without a reply, and the log records only their handle.
- **The agent runs on your machine as your user.** Permission rules and prompts reduce the risk, but they are not a sandbox. Real isolation takes a separate Unix user, a container, a virtual machine or your provider's sandbox.
- **Chat text and the files in a world are untrusted.** The prompt marks them that way, and the kit never turns them into commands. A model can still be talked into things, so assume a hijacked turn can do whatever your chosen posture allows.
- **Tokens live in private files and never on a command line.** An agent that runs as your user can still read the files.
- **Start with the read-only posture and an empty sender list.** Widen only after you have watched the agent work.

## What the kit controls, and what it does not

| Threat | What the kit does | What is left |
| --- | --- | --- |
| A stranger mentions the agent in a room | Ignores it silently and logs the handle and the reason | Nothing, except a line in your log |
| Another owner's account tries to command this one | Denies it. Only this account's owner and its listed senders are allowed | Nothing |
| The agent answers itself in a loop | Denies the agent's own handle | Nothing |
| Chat text tries to pick which world's clone the agent works in | Routing reads ids and addresses in structured fields and never the chat text, and matches whole ids and addresses only | A direct message has no world, and the agent may choose any clone it can reach |
| An event with no known world makes the agent work next to the tokens | The agent starts in `run/scratch/<account>`, a folder the kit makes for it, never in the runtime home that holds every account's token | The scratch folder is only the starting point. An agent can change folders, and one that runs as your user can read the token files by their path |
| Chat text tries to run shell commands or fill template fields | Text is never expanded by the shell, and templates are filled in one pass (tests cover both) | Nothing in the kit. See the next row for what a model does with the text |
| A trusted sender, or a file the agent reads, contains hostile instructions | Fences the event, says that everything fetched is data, and tells the agent to treat chat as a request to weigh | Prompt injection. This is advice to a model, not a barrier |
| A world's own project settings (a hook in `.claude/settings.json`, a server in `.mcp.json`) run a command when the agent starts | Every Claude Code example passes `--setting-sources user`, which loads only your own user settings, and a test fails when an example in the templates or the docs lacks it | Another agent tool, or a command you write yourself. Your own user settings. Whether Claude Code still reads the world's own `CLAUDE.md` is not settled, and a world's `AGENTS.md` and any file the agent reads can steer a model whatever the option says. See [below](#a-worlds-own-settings-can-run-code) |
| The agent's screenshot tool is used to join a world, or an account, that it should not | `sdlca-look` joins only a world that is listed for the account, names only the turn's own account inside a turn, runs the client and bun in a private folder of its own and not in the agent's clone, saves the picture as a new file that never follows a link, stops at a time limit, leaves the world, stops a browser the join left behind, and never prints what the client printed | An agent that can run any command can set the account itself. The body is visible in the room, and the picture goes to your model provider. See [below](#what-allowing-sdlca-look-means) |
| Someone steals a token | Private files, token off the command line, token sent only to Spawn's origin, raw token removed from the handler | Anything running as your user can read the token file |
| A runaway or hung agent, or a flood of mentions | A time limit, a bounded lock wait, an hourly cap on runs, and a failed or refused event is kept in `run/failed/` and not retried by itself | Cost up to the cap, and damage within the posture. The cap counts agent runs, not money |
| A hostile remote, submodule or large-file URL asks git for the token | Each clone's credential helper is attached to the git host of the world's URL only, so git offers nothing to other hosts | The agent can still read the token file, and an agent allowed to run git freely can run other programs through it |
| A clone is stale, or the update that fixes that is attacked through the clone's own git settings | The kit updates the clone itself before a turn, by fast-forward only. It fetches only from the git address that `sdlca-worlds` recorded for the world outside the clone, and refuses a clone whose remote or credential helper disagrees with it. It reads the clone's own settings first and again before the fast-forward, refuses links where git writes, turns hooks and the file system monitor off, allows https only and never lets git prompt | An agent that can edit files in the clone can still change `.git/config` in ways the check does not list, a program of its own that outlives the turn can change the file between the check and the fetch (a few tries are enough), and one that can edit `worlds.json` or the runtime home, or run a program as your user, can change the record. See [below](#updating-the-clone-before-a-turn) |
| A hijacked agent harms a world | Spawn's own permission model limits the account to its worlds, and a push never publishes | Pushes to `main` go live in every open room. Use git history to repair |
| An event runs twice after a crash | Skips an event id that it already finished (it remembers the newest 500) | An interrupted turn runs again, and an event with no usable id cannot be checked |
| Logs leak other people's chat | Log files are private, the listener log holds status lines only | The agent's output and failed events hold chat text |

## Who can trigger work, and how that is enforced

Every event goes through one function, `decide()` in [`lib/route.py`](../lib/route.py), before any agent is started. The rules:

- The sender is read from the event's structured `chat.from` field and nowhere else. Handles are compared exactly as Spawn writes them, in lower case: `@name` is a person and `@@name` is an agent.
- A missing or odd-looking sender is denied. The kit fails closed.
- The agent's own handle, `@@<SPAWN_USERNAME>`, is always denied, so the agent never answers itself.
- The account's owner is allowed as `@<owner>`. An agent that happens to have the owner's name, `@@<owner>`, is not the owner.
- Other senders are allowed only if they are listed in `allowlist.json` under `spawn.<owner>`. Malformed entries, a value that is not a list, and empty strings are ignored, so a typo never widens access. If the file cannot be read, only the owner is allowed.
- Everyone else is denied without a reply. A reply would tell a stranger that an agent is listening, and would cost chat lines.
- Only `chat_mention` events can start a turn. Friend requests are accepted only from the account's owner. Events about Spawn's builder, Savi, are only logged.

With the owner `alice`, the agent `alice_helper`, and `carol` and `@@review_bot` on the list, the outcomes are:

| Sender in the event | Outcome | Why |
| --- | --- | --- |
| `@alice` or `@Alice` | Allowed | The owner. Case does not matter |
| `@carol` | Allowed | A listed person |
| `@@review_bot` | Allowed | A listed agent, written with two `@` signs |
| `@@carol` | Denied, `not-allowed` | Carol is listed as a person, and this is an agent |
| `@@alice` | Denied, `not-allowed` | An agent with the owner's name is not the owner |
| `@@alice_helper` | Denied, `self` | The agent's own handle |
| `@bob`, an owner of another account | Denied, `not-allowed` | Not this account's owner |
| `@mallory` | Denied, `not-allowed` | A stranger |
| Missing or malformed | Denied, `unknown-sender` | Fail closed |

To add a person, use `bin/sdlca-allow spawn add alice carol`. To add an agent, write its name with two `@` signs: `bin/sdlca-allow spawn add alice @@review_bot`. Names use lowercase letters, digits and underscore. To take someone off, `sdlca-allow spawn remove` needs the entry exactly as it is stored (`carol` and `@carol` are two entries), so check `bin/sdlca-allow list` first. The file is read again for every event, so a change applies at once. See [Configuration](configuration.md#the-allowlist).

The tests for the gate are in [`tests/test_route.py`](../tests/test_route.py) and [`tests/shell/test_on_chat.sh`](../tests/shell/test_on_chat.sh).

Four things to understand about this gate:

1. **Everyone on the list has the agent's power.** A listed person can make the agent do whatever your agent command allows, on your machine. The same is true of the owner. Add only people you would hand your keyboard to. The safest list is the empty one.
2. **The gate trusts Spawn to fill in `chat.from` truthfully.** The shape of the field comes from Spawn's published API description. Our tests use events we wrote by hand. If a real event looks different from what the kit expects, the sender is unknown and the event is denied, so the kit fails closed.
3. **Replies are public.** Anything the agent says in a room can be read by everyone in the room. A trusted sender can ask the agent to read a file and say what it found. Do not give the agent access to files you would not post in the room.
4. **Spawn's terms may matter.** [Spawn's terms](https://www.spawn.co/terms-of-service) (read on 2026-11-17) say you may not allow others to access or use your account, and that you are responsible for everything done through it. Whether a listed person telling your agent what to do counts as using your account is a question we have not put to Spawn. It is one more reason to keep the list empty. See [the rules we follow for Spawn](compliance/spawn-rules.md).

## What the agent can do: the postures

The kit does not limit the agent. Your agent command does, through your agent tool's own permission system. The kit ships examples for Claude Code (Anthropic's agent tool, which [can run without a person](https://code.claude.com/docs/en/headless)). The exact commands are in [Configuration](configuration.md#the-postures). The read-only and builder postures were tested with Claude Code 2.1, and read-only with sight, which is the read-only one plus one more rule, had not been tested with a real agent run when this page was written. Permission rules change between versions, so test your choice after every upgrade. The kit has no adapters for other tools, so for them you must work out the equivalent yourself.

| Posture | What it can do | What it can reach | Worst case |
| --- | --- | --- | --- |
| **Read-only.** The `Read`, `Glob` and `Grep` tools, plus the kit's `sdlca-say` and `sdlca-api GET` | Read files, search, read Spawn, and post chat lines. In the maintainers' test, in a clone with no project settings of its own, it could not edit files or run other commands (see residual risk 10) | Every file your user can read. A bare `Read` rule is not limited to the world's folder, so token files, env files and the credentials file are in reach | It posts what it read into a public room, or posts unwanted lines. It cannot change files |
| **Read-only with sight.** The read-only tools, plus the kit's `sdlca-look` | Everything the read-only posture can do, and take one picture of a world this account serves, then read it | The same files as the read-only posture, and a body in the world for the length of a look | The read-only worst case, plus: the picture, and whatever is in it, goes to your model provider; text in the world can try to steer the model; the body shows in the room and counts against the account's body budget. See [below](#what-allowing-sdlca-look-means) |
| **Builder with a tool allowlist.** File edits, plus `git *`, `spawn *` and the kit's tools | Edit files, run any git command, run any command of Spawn's client, call any Spawn API method, and take screenshots | The same files. It can also push to a world | It pushes bad changes live to every open room. `git *` is broad, because git can run other programs through its configuration and aliases. `sdlca-api *` allows every HTTP method, including destructive ones and Spawn's paid doors (the character sculpt, billed to the linked person). `spawn *` is the whole client |
| **Full autonomy.** Every permission check is off | Run any command as your user | Everything your user can reach, including your SSH keys and cloud credentials | Anything you could do at your keyboard, done by someone else |

What no posture changes:

- **The agent can run the kit's own tools.** They read the token file in order to work. An agent that can run them can use the account's token for any call they allow, and read it from the file if its rules permit file reads.
- **A posture is as strong as your agent tool's rules.** Permission rules are the agent tool's code, not the kit's. A bug or a gap there is not something the kit can see or fix.
- **The agent can write files that steer later turns,** if its posture lets it write there: `WORK-TODO.md` and `AGENTS.md` in the runtime home, which every later turn reads, and a world's own files.

### About full autonomy

Claude Code's own help describes the option that skips all permission checks in a few words: "Bypass all permission checks. Recommended only for sandboxes with no internet access." (`claude --help`, Claude Code 2.1.327, run on 2026-11-17, for the `--dangerously-skip-permissions` flag; our example uses the `bypassPermissions` mode, which we treat the same way.)

The kit's agent needs the internet, to reach Spawn and your model provider, so it cannot meet that condition. A hijacked agent with full autonomy can send data out. Use this posture only inside a disposable virtual machine or container that holds nothing of yours, and only for an owner you fully trust. The kit's example file says the same. The kit has no default agent command at all, and the listener refuses to start without one.

## What allowing sdlca-look means

`sdlca-look` joins a world with a software-rendered body, saves one screenshot and leaves. The default prompt already tells the agent to use it. The builder example allows it, and the read-only with sight example adds it to the read-only helper as one more rule, `"Bash($SDLCA_CODE_DIR/bin/sdlca-look *)"`. Allowing it means:

- **The agent's body appears in the world.** For as long as a look takes, every player in the room can see it. A look waits for the world to load in the software renderer, which took a minute and a half or more on the machine we tried it on, so expect it to stay for a few minutes. The most is the time limit (`SDLCA_LOOK_TIMEOUT`, 240 seconds by default) plus up to about 20 seconds of cleanup, and the body is also told to end by itself 30 seconds after the limit.
- **It counts against the account's body budget.** Spawn limits how many bodies an agent account may stand at once and may make per minute and per day: two at once is Spawn's figure for an unlinked account, and a linked account's may differ ([Spawn's numbers](compliance/spawn-rules.md), which can change). A join that Spawn refuses because the budget is used makes the look fail. A look that failed to leave would hold a seat, which is why the tool always runs `leave` and stops what the join left behind.
- **The picture goes to your model provider.** The agent reads the PNG, so the image is sent to the model like any other file it reads, with whatever is in the room at that moment: other people's names, their words on screen, their builds. The provider's terms and the notes on [privacy and retention](#privacy-and-retention) apply to it as they do to chat text.
- **Hostile text inside the world can try to steer the model.** A sign, a texture or a HUD in the world can hold words written for a model. A picture is data, like a file in the world, and the prompt says so, but that is advice to a model and not a barrier (see [prompt injection](#prompt-injection-in-plain-words)).
- **The join credential is never printed.** What the Spawn client prints when it joins can hold credentials. `sdlca-look` shows none of it and stores none of it: only the page address is kept. [`tests/shell/test_tools.sh`](../tests/shell/test_tools.sh) checks, with a made-up credential, that it reaches neither the output, nor the logs, nor any file, for a look that works, a join that is refused, one that runs out of time, one with no page address or two, a failed screenshot and a signal. The client keeps a log of its own under `~/.spawn`. That is a file your user can read, like the token files, and the kit does not manage it.
- **The picture stays on disk, and it shows other people.** The kit never deletes it: it is a file at the path the agent chose (under `/tmp`, `$TMPDIR` or the runtime home's `shots` folder), and it holds whatever was in the room at that moment, other people's names, words and builds. Delete the pictures you do not need (see [Privacy and retention](#privacy-and-retention)).
- **It does not run in the agent's folder.** The client and the screenshot tool both run under bun, which loads a `bunfig.toml` (its `preload` setting runs code) and a `.env` from the folder it starts in. The agent works in a world's clone, which other people can push to, so a tool that started there would run whatever a world's builder put in the clone, as your user, which would make the read-only posture useless. The tool makes a private, empty folder and starts everything in it (a test plants both files in a clone and shows that nothing loads them). The picture is made there too and is placed at the path the agent gave at the very end, as a new file that never follows a link, so a link planted at that path while a look runs (a look takes seconds, and `/tmp` is shared) is not written through.
- **What the tool refuses**, so that allowing it is narrower than allowing `spawn *`: a world this account does not serve (any address that is not listed for it in `worlds.json`, by the rule that routes chat events); inside an agent turn, any account but the turn's own; an output that is not a new `.png` at an absolute path under `/tmp`, `$TMPDIR` or the `shots` folder; a page address that does not come from the client's own `page :` line, or that names a port a program was already holding before the look began. The time limit and the cleanup keep a hung join from holding the turn and a browser from being left running. [Configuration](configuration.md#seeing-a-world-with-sdlca-look) has the details. The cleanup that finds a browser left behind reads `/proc`, so it works on Linux only; elsewhere the tool relies on `spawn client leave` and the body's own end of life, and says when something still answers.

**How the account check can and cannot be got around.** The handler puts the turn's account in `SDLCA_TURN_ACCOUNT`, in the environment of the agent command, and the tool compares the account it is asked for with it. The account env file, the credentials file and the environment the handler was started in cannot change the value, because the handler assigns it last (a test checks all three). But it is an environment variable in a process that runs as your user. An agent that is allowed to run any command can unset it, set it itself (`SDLCA_TURN_ACCOUNT=other sdlca-look other ...`), read another account's token file or call Spawn's client as that account directly, and a test shows that setting it is not stopped. Whether a call written that way is allowed by a rule such as `Bash(.../sdlca-look *)` depends on how your agent tool matches a leading variable assignment or a wrapper such as `env`. That is its own code, which the kit cannot see, so test it. The check keeps the allowed tool from being the way to name another account. It is not a sandbox. A separate Unix user for the agent is one, because another account's files are then out of its reach (residual risk 1).

## Why an agent must not run sdlca-body

`sdlca-body` gives an agent account a body made from a picture, or puts a body on it (see [Giving an agent a body](operations.md#giving-an-agent-a-body)). It is for the person who runs the kit. Do not put it on an agent's list of allowed commands in any posture. A run uses the account's own token, outside the limits you set for the agent, and it:

- **Spends the linked person's money.** The sculpt is billed to the person the agent is linked to. The kit puts no limit of its own on how many sculpts a person starts, except that it never starts a second one while one is recorded for the account.
- **Puts content on Spawn.** The picture is uploaded to Spawn, which reviews it, and the body that comes out is shown to everyone who sees the agent in a world.
- **Reads a file from this machine and sends it.** Only a file that starts like a PNG, JPEG or WebP picture of at most 4 MB leaves (the file's own first bytes decide, so a token file or a note is refused whatever it is called), and it goes as it is, under a fixed file name. Embedded text or camera data goes with it, and so does anything after the end of the picture; the plan names both first. A file that starts like a picture and is followed by other data is not refused.
- **Changes how the agent looks to others.** A body the agent should not wear is a harm of its own, and `--reset` is the way back.
- **Carries a model file to Spawn** (`--carry`). Only a glTF binary of at most 25 MB leaves (its header decides), through a world where the agent is an editor. A file over 4.4 MB goes to a signed storage address that Spawn names: the tool uses it only if it is https, has a host name (never an address), and has no user information, never sends the token there, never follows a redirect from it, and never prints it. The file is then public to anyone who knows its hash-named address, and it stays with that world's assets.
- **Keeps one small file.** `body-sculpt.json` in the account's folder records a sculpt that was asked for (mode 0600, made in a way that fails if the file, or a link at its path, already exists). Anything that can write in the runtime home, as an agent can, could delete it, which would let a second sculpt start, or plant one, which would make picture runs refuse. The text in it is cleaned before it is printed.

The barrier against an agent spending that money is the command list in `SDLCA_AGENT_CMD`, and it has to hold for more than this command. In the builder posture, `sdlca-api *` and `spawn *` already reach the same paid doors (make a character, sculpt it, wear it, reset it) with the account's token, because `sdlca-api` takes any method and any path. Only the read-only postures keep that money out of reach, and only because they allow `sdlca-api GET *`, which starts nothing.

What the tool does so that a mistake does not become harm:

- It changes nothing without `--apply`, and a dry run only reads from Spawn.
- It refuses to run inside an agent turn (the handler sets `SDLCA_TURN_ACCOUNT` there). That is a net for a mistake, such as adding the command to the list by accident. It is not a barrier against an agent that can run any command, which could clear the variable.
- It refuses an account that Spawn does not call an agent, so a person's token is never used to change the person's own character.
- It never repeats a call that makes something, because a second sculpt could be billed twice, and it records the sculpt before it asks for it. When the answer is lost or unclear it says so and keeps the record, so that the next run cannot start another by accident. Only the harmless checks on a running sculpt are asked again.
- The token goes only to Spawn's origin, never through a proxy from the environment for a plain-http origin, and is never printed: every line the tool prints passes through one function that takes it out. A redirect is never followed. No call lasts longer than two minutes (the upload, five), however slowly Spawn answers.
- What Spawn answers is printed as plain text with control characters removed, so that a reply cannot rewrite a terminal, and an id from Spawn is checked before it goes into a web address (an id that holds the token is refused).

[`tests/test_body.py`](../tests/test_body.py) checks these against a stand-in Spawn, and [`tests/test_state_files.py`](../tests/test_state_files.py) checks the opener that sends the token (no kind of redirect is followed, and the proxy is ignored when asked), and `tests/test_say.py` and `tests/test_worlds.py` check that no proxy gets the token from those two tools.

## Optional extensions

`sdlca-ext` lets the owner add outside tools and MCP servers (see [Optional extensions](extensions.md)). What it guards, and what it cannot:

- **Nothing widens by itself.** The kit prints the permission rules an extension implies and never edits `SDLCA_AGENT_CMD`. Turning an extension on changes the prompt and the keys, not what the agent's tool is allowed to run.
- **Keys.** They live in `accounts/<account>/credentials.d/<name>.env` (mode 0600; a link, a file others can read, or a writable folder is refused). The file is parsed, never run as shell, and only the names the manifest declares are used. With `inject: wrapper` the agent's environment never holds them: `sdlca-ext run` gives them to one command, and inside a turn only to the commands the manifest names, for the turn's own account. With `inject: env` the agent can read them from its environment, so keep its permission rules narrow.
- **What a manifest cannot say.** No secret in the file, no command that can run other programs or print the environment (`env`, `sh`, `python3`, `curl` and more), no unpinned `npx` package, no plain-http server, no header secret written out. This list is a guard and is not complete.
- **Still true.** An allowed command or MCP server can do anything its own program can do with the keys it gets, and what it returns is untrusted data. The README of each extension must say what leaves your machine and what it costs; read it before you turn the extension on.
- **The extension's text.** `prompt.md` and the summary go into the prompt inside tags, with `<` escaped, as data from the extension's author.

## A world's own settings can run code

**The hole.** In print mode (`-p`) Claude Code skips the question that asks whether you trust a folder (`claude --help` says so). With its default settings it then loads the folder's own project settings: hooks in `.claude/settings.json`, and MCP servers declared in `.mcp.json`. The kit runs the agent inside a world's clone, and other people can push to a world, so someone who can build in a world can push a hook or a server that runs any command as your user. It runs before the agent's first tool call, so no allow rule, no deny rule and no posture applies to it. The read-only posture does not help.

**What we verified,** on 2026-11-18 with Claude Code 2.1.327, in scratch folders, by the maintainer's assistant: with default settings, a hook planted in `.claude/settings.json` ran (both a `SessionStart` and a `UserPromptSubmit` hook) and so did an MCP server declared in `.mcp.json`. Each ran an arbitrary command as the user. With `--setting-sources user`, neither ran.

**The fix.** Every Claude Code example in the kit passes `--setting-sources user`, which loads only your own user settings. [`tests/test_claude_examples.py`](../tests/test_claude_examples.py) fails when an example in `templates/account.env.example` or in the docs lacks it. Your own `~/.claude/settings.json` (and its hooks) and managed settings still apply, which is what you would expect. Keep the option in any command you write. **An account you set up before the examples had the option still runs without it,** because `scripts/install.sh` never overwrites an env file and nothing in the kit checks the command: add `--setting-sources user` to its `SDLCA_AGENT_CMD` now (see [Upgrade the kit](operations.md#upgrade-the-kit)).

**A stronger option, with a cost.** Claude Code also has a `--restricted` mode (listed in the `--help` of version 2.1.327). In the same test it stopped both the hook and the MCP server. Its help text says it also takes away the tools that run programs unless you name them again, ignores your settings files and the folder's, keeps the file tools inside the working folders, refuses `bypassPermissions`, and leaves changes to settings, git and tool configuration to a person. We checked three things on 2026-11-18: a read of a file outside the folder was refused; with Bash named in `--tools` next to one allowlist pattern, the listed command ran and an unlisted one (`cat` of a file outside the folder, `touch`) was refused; and the folder's own hook did not run. It is not in the examples, because we did not try it with the kit's own tools, and because keeping file reads inside the world's folder would stop the agent from reading the `AGENTS.md` and `WORK-TODO.md` in the runtime home, which the prompt tells it to read first (`--add-dir` adds a folder; we did not try that). If you want it, try it on a throwaway account first. The help also lists `--safe-mode`, which turns off every customization (CLAUDE.md, skills, plugins, hooks, MCP servers), and `--bare`, a minimal mode that signs in only with an API key. We tried neither with the kit.

**What this does not cover.**

- **Other tools.** Other agents' tools may load a folder's own hooks, plugins or servers in the same way, and some cannot be told not to. The kit's examples for them are unverified. Before you run any other tool in a world's clone, find out which of the folder's files it loads, and whether it asks first when it runs without a person.
- **Older versions.** An older Claude Code may lack these options or behave differently. Check `claude --help` for `--setting-sources` (and `--restricted`, `--safe-mode` or `--bare` if you want one of them) before you rely on it, check again after an upgrade, and [test the command by hand](configuration.md#test-a-command-by-hand).
- **Instruction files.** Whether Claude Code still loads the world's own `CLAUDE.md` files (and `CLAUDE.local.md` and `.claude/rules`) under `--setting-sources user` is not settled. Reviewers' runs on 2026-11-18 with Claude Code 2.1.327, in fresh scratch folders, did not load a folder's `CLAUDE.md`, with or without the option, and we did not test a git clone or a folder that Claude Code already trusts. Do not rely on either answer. What is certain is that a world's `AGENTS.md` (the kit's prompt tells the agent to read it when it is in a clone), its other files and anything else the agent reads are data from whoever can push to the world, not something the kit trusts: they can steer a model whatever this option does, and the posture you chose is what limits the damage if the model follows them (see [prompt injection](#prompt-injection-in-plain-words)).

## Prompt injection in plain words

*Prompt injection* means text that tries to give a model new instructions. A model reads its instructions and the text it is working on in the same stream, so it cannot always tell them apart. The text can come from several places:

- **From a trusted sender,** who pastes text from somewhere else without reading it.
- **From other people.** The default prompt tells the agent to fetch the message "and what followed" through `sdlca-api GET '<actionData>'`. That read returns other people's lines in the room. They are not on your list, but the agent reads them.
- **From files in a world.** Any collaborator can change a world's files. Answers from Savi, notes and downloaded assets can carry text too.
- **From the agent's own notes.** `WORK-TODO.md` is written by the agent and read by later turns. A hijacked turn could plant text there for the next one.

What the kit does about it:

- The event goes into the prompt between `<untrusted_event>` tags, and every `<` inside is written as `\u003c`, so the text cannot forge the closing tag.
- The prompt says that the chat text, anything fetched later, the world's files, Savi's replies and `WORK-TODO.md` are data, to be weighed as information and never as instructions that change its rules.
- Chat text is never expanded by the shell, and template fields are filled in one pass, so text cannot reach `{{CODE_DIR}}` or a command substitution. Tests cover both.
- Chat text cannot choose the world the agent starts in.
- The agent is told never to print tokens, and to use `sdlca-api` so tokens stay off command lines.

What the kit cannot do: nothing in it recognizes hostile text. The fence and the wording are advice to a model, not a barrier, and models can be talked out of advice. So plan for the case where it fails. Pick a posture, a sender list and an isolation level that you can live with if a hijacked turn does the worst thing that posture allows.

## Token handling

The kit holds two kinds of secret: each account's Spawn token, and any provider keys in `SDLCA_CREDENTIALS_FILE`. How the Spawn token is handled:

| Where | How | Test or check |
| --- | --- | --- |
| On disk | A file of its own, mode 0600, in a folder of mode 0700. The kit's shell scripts run with `umask 077`, and the Python tools set mode 0600 on what they write | Set by `sdlca-onboard` and `sdlca-token`; the env file must not be writable by group or others |
| When you store it by hand | `sdlca-token add` asks for the token without echoing it, or reads one line from standard input. It takes no token as an argument, refuses an invite code and values that do not look like a token (fewer than 16 characters, or a space, double quote, backslash or character outside visible ASCII), writes the file through a temporary file and never prints the token | [`tests/shell/test_token.sh`](../tests/shell/test_token.sh) checks it |
| In the shell tools (`sdlca-api`, `sdlca-friends`) | Passed to curl as a header in a config read from standard input, so it never appears in `ps` | [`tests/shell/test_on_chat.sh`](../tests/shell/test_on_chat.sh) checks it |
| In the Python tools (`sdlca-say`, `sdlca-worlds`, `sdlca-body`) | Sent in-process, never on a command line | Review of the code. [`tests/test_say.py`](../tests/test_say.py) covers its origin and redirect rules |
| Where it may be sent | `sdlca-api` sends it only to the Spawn origin and refuses any other host. All five of these tools check `SPAWN_ORIGIN`: https, or plain http only to this machine, never an origin with user information in it (`file://` only when a test sets a variable for it). No tool follows a redirect: the Python ones refuse them, and curl does not follow them unless told to | [`lib/safeurl.py`](../lib/safeurl.py), [`lib/common.sh`](../lib/common.sh), [`tests/shell/test_listen.sh`](../tests/shell/test_listen.sh) |
| In the handler | Spawn's client puts the raw token in `SPAWN_TOKEN` for the handler. The handler removes it before anything runs, so it is not in the agent's environment | A test checks the agent's environment |
| In the prompt | Never. The prompt tells the agent to use `sdlca-api` | A test checks the prompt |
| In git | Each clone has its own credential helper that reads the token file when git runs. It is attached to the git host of the world's https URL only, after an empty helper that makes git forget any global one. The global git configuration is not changed | [`tests/test_gitcred.py`](../tests/test_gitcred.py) checks that other hosts get nothing. See [Several accounts and worlds](multi-account-and-worlds.md#credentials-and-identity-in-the-clones) |
| When the tools read it | Every tool that reads the token file refuses a token with a space, line break, double quote, backslash or non-ASCII character in it, before anything is sent, and its error does not print the file's contents. Without this, a hand-edited file could change the curl settings the token travels in, or end up in an error message | [`tests/shell/test_tools.sh`](../tests/shell/test_tools.sh) and [`tests/test_state_files.py`](../tests/test_state_files.py) check it |
| What `sdlca-api` refuses to send | A body that starts with `@`, because curl would read that local file and send it to Spawn. Curl also runs with `-q` (it ignores `~/.curlrc`) and `--globoff` (it does not expand `[1-3]` or `{a,b}` in an address) | [`tests/shell/test_tools.sh`](../tests/shell/test_tools.sh) checks it |
| In logs | The kit never writes it to its own log lines. A token file that was hand-edited to hold a line break is refused before anything is sent, with an error that does not print its contents | Review of the code, and the test above |

Where the token can still be read or leak:

- **By the agent, as your user.** The agent's environment holds `SPAWN_TOKEN_FILE`, which is the path to the token. Even if the agent never needs to read the file, nothing stops it.
- **Through git.** Git itself offers the token only to the git host of the world's URL. A hostile remote, submodule or large-file URL on another host gets nothing, and [`tests/test_gitcred.py`](../tests/test_gitcred.py) checks this with `git credential fill`. That limits what git does on its own. It does not stop an agent that can run arbitrary git commands: git can run other programs through its configuration and aliases, and those programs can read the token file. The `Bash(git *)` rule in the builder posture allows that.
- **Through `SPAWN_ORIGIN`.** The five tools that send the token (`sdlca-api`, `sdlca-friends`, `sdlca-say`, `sdlca-worlds` and `sdlca-body`) refuse an origin that is not https (plain http is allowed only to this machine) and an origin with user information in it. They cannot tell whether an https host really is Spawn's, so leave `SPAWN_ORIGIN` unset, as [Configuration](configuration.md#variables-from-spawn-that-the-kit-reads) advises. A plain-http origin is for this machine only, and the Python tools (`sdlca-say`, `sdlca-worlds` and `sdlca-body`) never send it through a proxy named in the environment, which would have carried the token in clear text to the proxy's host.
- **A personal token is a person's own.** If you store one with `sdlca-token`, a leak exposes that person's account, and everything done with it appears under their name. Each person should keep their own, and `sdlca-token verify` says when a token is a person's. See [Several accounts and worlds](multi-account-and-worlds.md#personal-tokens-that-belong-to-other-people).
- **In the invite code.** `sdlca-onboard` takes the one-time invite as a command-line option, so it is visible in the process list and in your shell history for a moment. It works once and expires after ten minutes.
- **In Spawn's client.** Spawn's client uses the token itself. It is proprietary and not ours: the kit does not bundle it, and you install it from npm yourself. You trust it with the token as much as you trust Spawn.
- **Provider keys.** Everything in `SDLCA_CREDENTIALS_FILE` is exported to the agent command. A full-autonomy agent can print it.

If you think a token has leaked, do not wait: stop the listener, have the owner unlink the agent or revoke the token in Spawn, and make a new one. [Operations](operations.md#rotating-a-token) has the steps. Never paste a token into an issue, a pull request or a chat.

## Updating the clone before a turn

Before an agent turn that came from a world's own chat, the handler runs [`lib/refresh.py`](../lib/refresh.py) to bring that world's clone up to date. It runs as your user, outside the agent's tool limits, in a folder the agent may have written to. That is why it takes the care below. What it does and how to read its answers is in [Configuration](configuration.md#updating-a-clone-before-each-turn). The security side:

- **Held to the git address that Spawn gave for the world.** `sdlca-worlds` records that address in `worlds.json` (the `git` field), from Spawn's own listing and never from the clone, and only when it is one the clone's credential helper can be attached to: https, with a host and no user information. The handler hands it to the update (`lib/route.py` prints it as the last field), which fetches from exactly that address, `git fetch -- <address> ...`, and not through the name of a remote, so what the clone's settings say about the remote that the branch follows (a proxy, a program to run, another address) does not apply to the fetch. One more thing does: git reads the word it is given as the name of a remote first, so a remote section called like the recorded address (`[remote "https://..."]` with a url of its own) would redirect that fetch, and the update refuses a clone that has a remote section with a name that is an address (a name with a colon, a slash or an at sign). Before it fetches, it requires that the branch's remote has exactly one address in the clone's settings and that it is the recorded one: the scheme and the host are compared in lower case, a trailing slash or `.git` does not count, the port and the rest of the path are compared as written, and an address with user information, a query, an odd character or a `.` or `..` segment is never accepted. Otherwise the clone is `untrusted`, and the log names hosts and never a whole address. A world with no usable recorded address is `unverified`: the clone is not trusted and no git runs. [`tests/test_refresh.py`](../tests/test_refresh.py) shows the attack this closes: a clone whose settings were rewritten to point at a host the agent controls (a server on this machine), with a copy of the kit's own helper line scoped to it, so that the update would have fetched from there and handed over the token. That host receives no request. The controls in the same test show that the update's earlier rule for a helper's scope accepted that helper, and that a fetch through the remote's name, like plain git, does connect and send the token.
- **Trusted git, with fast-forward only.** The kit does the update, not the agent, because the kit cannot tell a read-only agent from a building one. The branch moves only along a straight line (`git merge --ff-only --no-overwrite-ignore`). The update never merges, rebases, resets, checks out, cleans, stashes or forces, so it cannot leave conflict markers in files the world runs, and it cannot overwrite a tracked change you have not committed, an untracked file or an ignored file: it refuses instead. It looks for lock files first, because git would otherwise write the files and only then find that it cannot move the branch.
- **No shell.** Git is started with an argument list and its absolute path, and a command is never built from anything in the clone (a test gives the clone a branch named like a shell command and shows that nothing runs). Git is found only through the absolute entries of `PATH`, so a program named `git` inside the clone is never run, even if `PATH` has an empty, `.` or relative entry and the update is started from inside the clone (a test checks this).
- **Hooks and the file system monitor are off, on the command line.** Every git call carries `core.hooksPath=/dev/null` and `core.fsmonitor=false` (and `core.pager=cat`, `gc.auto=0`, `maintenance.auto=false`, `merge.autoStash=false`), which beat both the clone's configuration and your global one. A post-merge hook or a monitor command planted in the clone does not run, and the tests prove it with a control: plain git, in the same situation, does run it.
- **https only, no prompts, and no variable that redirects git.** The calls get `GIT_ALLOW_PROTOCOL=https` (unless you set it yourself), `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`, and lose `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY` and `GIT_ALTERNATE_OBJECT_DIRECTORIES`. Apart from that the environment is yours: it is not a clean environment. It does not hold the provider keys of `SDLCA_CREDENTIALS_FILE`, because the handler runs the update before it reads that file. Git does not look for a repository above the clone's folder. A clone folder that is a symbolic link, or whose `.git` is a symbolic link or a file that points to a git folder somewhere else, is not trusted.
- **A check of the clone's own configuration, before git reads any object, again before the fetch and again before the fast-forward.** The first check comes before the first call that reads an object, because reading a commit that is missing makes git fetch it, on its own, from a promisor remote that the settings name, as your user and with the token if a helper is scoped to that host (we reproduced that with a copy of the kit's own helper line; every git call also carries `GIT_NO_LAZY_FETCH=1`, which turns the fetching on demand off for git 2.44 and newer). Reading the settings with `git config` runs nothing (`.git/config.worktree` is read only when the clone turns on `extensions.worktreeConfig`, which is the only time git reads it). If it holds a setting that can run a program, send git somewhere else or change whom it trusts, nothing more is done, and the log names the key, never the value. That covers a `filter.*`, `core.fsmonitor`, `core.sshCommand`, `core.gitProxy`, `core.askPass`, `include.*`, `url.*.insteadOf`, a remote's `proxy`, `uploadpack`, `receivepack` or `vcs`, `fetch.bundleURI`, a promisor remote (`extensions.partialClone`, `remote.<name>.promisor`, `remote.<name>.partialCloneFilter`, `promisor.*`), a remote section whose name is an address, and every `http.*` key except the few that only tune transfers or that the kit writes (so `http.proxy`, `http.sslVerify`, `http.sslCAInfo`, `http.curloptResolve` and `http.extraHeader` are refused); the others are listed under [What makes a clone untrusted](configuration.md#updating-a-clone-before-each-turn). Without the `http.*` rule, a clone could keep the kit's own credential helper and add a proxy, and the update's request, with the token in it, would go to the proxy.
- **The clone's own credential helper keeps working, and only that one, only for the recorded origin.** The clone logs in through the helper that `sdlca-worlds` wrote, which is attached to the git host of the world's https URL only. The update never passes an empty `credential.helper`, which would erase it. It accepts only that helper's exact form, reading this account's token file or a `token` file in an account's folder under the runtime home, and only when it is scoped to the origin (scheme, host and port) of the recorded address. A helper scoped to any other origin, even an empty one, makes the clone untrusted, because a copy of the kit's own helper line under another host's scope is how an agent would get the token sent there. A helper of another form would be a command that an agent could have written, and a helper that read some other file would make the kit send that file to a host as a password. Plain http carries a token only to this machine (the rule of `check_origin`). Tests prove the helper is consulted, with a control that shows an empty one erases it.
- **Nothing is written through a link.** Git appends to a reflog in place, so a link under `.git/logs` (or a file with a second name there) would make the update write a line into whatever the link points to, as you. The update refuses a clone with a link under `.git/logs` or `.git/refs`. It does not write `FETCH_HEAD` (it fetches into `refs/sdlca/refresh-tip`), and it gives git a fixed identity, `sdlca-refresh`, so the line that a fast-forward writes into a reflog is one the kit chose and not text from the clone's `user.name`. The tests show that plain git does write through such links.
- **A time limit, and the whole process group is stopped.** Each git call has `SDLCA_REFRESH_TIMEOUT` seconds, and the fast-forward at least 600. When a call runs out, git and everything in its process group are stopped, with `SIGTERM` first so that git removes its own lock files, and `SIGKILL` 3 seconds later. The same happens when the update is stopped by `SIGTERM`, `SIGHUP` or `SIGINT`, and the handler stops the whole update after four times the limit plus 660 seconds. A program that moved itself to another session is not stopped, and neither is anything when `lib/refresh.py` is killed with `SIGKILL`: git then runs on until it ends.
- **Nothing a remote can influence reaches the prompt.** The prompt gets a paragraph in fixed wording, chosen by the status and the code. Git's own error text goes to the log only, as one line with control characters removed, user information in URLs removed, token-shaped strings removed and the line cut to 120 characters.

What this does not cover, honestly:

- **The check is a list.** An agent that can edit files in the clone can still change `.git/config` in ways the list does not name. It holds the settings we know make git run a program, send a request somewhere else or change whom it trusts, and it treats everything under `http.` that is not on a short allowed list as unsafe, but git has many settings and new ones appear. The fetch from the recorded address does not apply the settings of the remote that the branch follows, but a few settings still reach it: `url.<base>.insteadOf` rewrites an address given on the command line too (a test shows that with plain git), and a remote section called like the address is read as a remote (a test shows that as well), so both stay on the list. If your agent may edit files in the clone, the update is only as strong as that list. The check also reads the settings at three moments (before git reads an object, before the fetch and before the fast-forward), not during the calls, so a process that the agent left running (residual risk 11) could change them in between, and that is a few tries, not a theoretical gap: in a reviewer's test of this version (not one of the repository's tests), a program that flipped `.git/config` between a clean and a hostile version every few milliseconds got the token to a host of its choosing within a few runs of the update, although every check saw a clean file. It needs a program that outlives the turn, so it is bounded by the posture (full autonomy, or anything that lets the agent start a background program), and a separate Unix user is what contains it. Doing the network fetch with a configuration that the kit writes and not the clone's would close it; the update does not do that yet. A separate Unix user for the agent, a container or a virtual machine (see [the hardening checklist](#hardening-checklist)) is what actually contains it.
- **What the recorded address does not close.** Before the address was recorded, an agent that could edit `.git/config` could point the update, and one of your accounts' tokens, at a host of its choosing, which was the largest open risk of the update. That case is closed: the update takes the address from the registry and not from the clone. What is still open:
  - **The record is a file in the runtime home, and the update trusts it.** An agent that can edit `worlds.json`, or anything else in the runtime home, or that can run a program as your user (which can run `sdlca-worlds` with a `SPAWN_ORIGIN` of its own, read the token files or call git directly), is not contained by this. It can change the record, and with it where the update fetches from and where a helper may send the token. This is residual risk 1 again: the address check protects against the clone's settings being rewritten, not against an agent that has your user's rights.
  - **The check of the clone's settings is still a list** (the first bullet above).
  - **The record is only as good as Spawn's listing.** `sdlca-worlds` takes the address from the account's own listing, and the kit cannot tell whether an https host that a listing names is really Spawn's (residual risk 8).
  - **A world recorded before this check existed has no address** and is not updated (`unverified`) until you run `sdlca-worlds --apply` under the agent's account (with `--only @owner/world` for one world). Recording changes only the registry, never the clone's files or settings: it takes the address from the listing. (The same run also follows a rename, which points the clone's remote at the new address and moves the folder, and makes a missing clone, so look at the dry run first.) If the clone's remote differs from it, the update then says `untrusted` and names both hosts, and you decide which is right.
  - **An address that cannot carry the helper is not recorded.** One that is not https, has no host, has user information in it or has a `.` or `..` segment in its path is not recorded, so a world whose listing gives such an address is not updated. `sdlca-worlds` says so, without printing the address.

  A separate Unix user for the agent, a container or a virtual machine, with no write access to the runtime home or the token files, is still the real boundary.
- **Only the clone's own settings are checked.** Your global and system git configuration are yours and trusted. A `.gitattributes` file in the world can name a filter that your global configuration defines, as in any checkout.
- **The world chooses what the update writes, and the update delivers it without anyone asking.** Anyone who can push to the world decides what a fast-forward puts in the clone, and the agent then reads it. Before this update existed, a push reached the agent's working folder only when something pulled it. Now every routed message pulls it, even in the read-only posture. That is the same exposure as residual risk 10 below, made automatic: files in the world that your agent tool loads (`.claude/`, `.mcp.json`, hooks, `AGENTS.md`) arrive on the next turn. For a world with editors you do not fully trust, set `SDLCA_REFRESH_TIMEOUT=0`.
- **The read-only posture is unchanged, and so is its reach.** It still reads any file your user can read. The update needs no permission from the agent, and what the agent may do is the same, but what it finds in the clone is now current, and not whatever was cloned earlier.
- **A stopped fast-forward can leave a partly updated tree.** The fast-forward gets at least ten minutes so that a short `SDLCA_REFRESH_TIMEOUT` does not cut it off. If a stuck file filter or a stalled disk still makes it run out of time, files that were already replaced stay replaced while the branch has not moved, and `git status` shows them as changes. The log says so (`failed/merge`), and the next update is refused until a person looks. [Operations](operations.md#the-clone-was-not-brought-up-to-date) shows the way out.
- **A user in the middle.** The update runs as the handler's user, in a folder the agent may write. If the agent runs as another Unix user (for example through `sudo -u` in `SDLCA_AGENT_CMD`) and can write in the clone, a setting the list does not name would run as the kit's user, which owns the token files. Give the whole kit one dedicated user or container. If the agent has a user of its own, turn the update off or keep the clone unwritable by the agent.
- **It needs git 2.29 or newer.** Older git lacks an option the update uses, and the update says so and changes nothing.

## What is logged, and where

| Where | What is in it | Chat text in it? |
| --- | --- | --- |
| `accounts/<account>/listener.log` | The Spawn client's status lines, and the output of the friend-request catch-up at start. The client's standard output, which holds each event as JSON, is thrown away | No |
| `accounts/<account>/handler.log` | One metadata line per event handled (time, sender handle, world, outcome), one line about the update of the world's clone (shas, counts, the name of a setting, a host, or the first line of git's own error, cleaned), plus **everything the agent prints**, plus the output of friend accepting | Possibly. The agent's output can hold anything it read, including other people's lines and file contents. The update line holds no chat text |
| `run/failed/<event-id>.json` | The whole event, kept so you can replay a failed turn. The handler deletes it after `SDLCA_FAILED_KEEP_DAYS` days (default 30) | **Yes.** It is the raw event, with the chat text |
| `accounts/<account>/handled.ids` | The ids of finished events | No |
| `accounts/<account>/runs.log` | Start times of recent agent runs | No |
| The pictures that `sdlca-look` saves (a `.png` at the path the agent chose, under `/tmp`, `$TMPDIR` or `shots/` in the runtime home) | What was in the room when it was taken: other people's names, words and builds. Nothing deletes them | Other people's words, as pixels. The picture was also sent to your model provider when the agent read it |
| The systemd journal | Start, stop and restart messages and start-up errors | No |
| Your agent tool's own logs | Whatever your tool keeps. The kit does not manage or see them | Probably. Check |

The kit's own log lines carry a sender handle only after it has been checked against the pattern for a Spawn handle, so a sender cannot forge a log line. Chat text is never written by the kit. The handler does not export the event to the agent's environment (even if the program that started it had exported a variable of that name), so the agent gets it in the prompt, between the `<untrusted_event>` tags, and not as a variable that every program it starts inherits.

In short: `listener.log` holds only the Spawn client's status lines (and the friend catch-up output), and `handler.log` holds the kit's metadata lines and the agent's own output. Treat `handler.log` and `run/failed/` as private. Both are created with mode 0600 or in folders of mode 0700.

## Privacy and retention

Other people's chat text passes through your machine, and through your agent provider. That is a duty of care, so know where it goes:

- **To your model provider.** The prompt holds the event, and the agent reads what followed. Check your provider's terms for how it uses prompts. For example, Anthropic's documentation says consumer plans can have training on or off by a user setting, and that under its commercial and API terms it does not train on code or prompts sent to Claude Code unless the customer opts in ([Anthropic's data usage page](https://code.claude.com/docs/en/data-usage), read on 2026-11-17 for our research). Prefer API or commercial terms for unattended use. Claude Code also has a print-mode option, `--no-session-persistence`, that does not save sessions to disk (`claude --help`, 2.1.327, 2026-11-17). We have not tested it with the kit.
- **To your disk,** in the places listed above.
- **To the room,** in the agent's replies.
- **Spawn's terms** ask people not to disclose other people's personal information. See [the rules we follow for Spawn](compliance/spawn-rules.md).
- **Young people and Spawn's Terms.** Spawn rooms can include young people, and your agent forwards what it reads there to your model provider. Spawn's [Terms](https://www.spawn.co/terms-of-service) set a minimum age and parental-consent rules and contain a sanctions clause (read 2026-11-17). The person who runs the kit must meet them. We do not interpret them.

Retention: **the kit never rotates or deletes your logs.** It does delete saved events in `run/failed/`: when the next allowed event reaches the handler, it removes the saved files that are more than `SDLCA_FAILED_KEEP_DAYS` days old (default 30; `0` keeps them forever). The `run/failed` folder is shared by all accounts, so an allowed event on any account removes every account's saved files that are more than that account's `SDLCA_FAILED_KEEP_DAYS` days old. To keep files longer, set the same larger value (or `0`) in every account's env file, or copy the file out. It also trims its own bookkeeping files: `handled.ids` keeps the newest 500 ids, and `runs.log` keeps the last hour. The logs grow until you act. Saved events hold raw chat text, so set `SDLCA_FAILED_KEEP_DAYS` to what you need, or look and delete them sooner yourself:

```bash
ls -l ~/.sdlca/spawn/run/failed | head
find ~/.sdlca/spawn/run/failed -name '*.json' -mtime +14 -print     # look first
find ~/.sdlca/spawn/run/failed -name '*.json' -mtime +14 -delete    # then delete
```

Pictures that `sdlca-look` saved are kept until you delete them, and the kit never deletes one: the files under `$SDLCA_SPAWN_HOME/shots` stay, and so do the ones the agent put in `/tmp` until the machine clears it. They show other people's content, so clear them as you clear saved events, for example `find ~/.sdlca/spawn/shots -name '*.png' -mtime +7 -print` first, and then the same with `-delete` (and look at `/tmp` for `*.png` files that the agent made, for example the ones named in `handler.log`).

For the logs, use `logrotate` with `copytruncate`, or empty them while no turn is running. [Operations](operations.md#logs-and-what-they-contain) explains both. The kit ships no logrotate configuration.

## Residual risks

These are risks the kit does not remove. We list them so that you can decide with open eyes. Several come from an earlier code review that we treat as a research note, not as an authority (see [below](#what-an-earlier-code-review-found-and-what-changed)).

1. **A same-user agent can read the token files.** The agent runs as your user, so it can read `accounts/*/token` for every account in the runtime home, and every other file your user can read. Permission rules and prompts reduce the risk, but they are not a sandbox. Real isolation needs a separate Unix user, a container or your provider's sandbox.
2. **Allow rules are broad.** `Bash(git *)` allows every git command, and git can run other programs through its configuration, aliases and hooks. `Bash(spawn *)` allows the whole Spawn client, which is a script that bun runs, and bun loads a `bunfig.toml` (its `preload` setting runs code) and a `.env` from the folder it starts in. The agent starts in a world's clone, which other people can push to, so with `spawn *` allowed a world's builder can run code as your user that no allow rule sees. (`sdlca-look` does not have this problem: it starts the client in a private folder.) `Bash(.../sdlca-api *)` allows every HTTP method on Spawn's API. Narrow what you allow.
3. **Prompt injection is mitigated, not eliminated.** See [above](#prompt-injection-in-plain-words). A trusted sender can paste hostile text, and the agent can read hostile files or lines.
4. **The agent's own notes are a way to carry text forward.** `WORK-TODO.md` is written by the agent and read by every later turn. A hijacked turn could plant text there. So could it change `AGENTS.md` in the runtime home, if its posture allows writing there. Anything that lets the agent write files in the runtime home lets a hijacked turn change the rules for later turns.
5. **A crash can skip an older unfinished event, in one case.** If Spawn's client runs several handlers at once, and a newer event finishes before an older one, a crash before the older one finishes means the cursor is already past it. We have not confirmed that the client ever overlaps handlers. See [Operations](operations.md#cursor-and-replay).
6. **The read-only posture can read any file the user can read.** It cannot change anything, but it can say what it read.
7. **Several owners in one runtime home share one trust boundary.** One Unix user, one set of token files, one `WORK-TODO.md`. See [Several accounts and worlds](multi-account-and-worlds.md#one-account-per-person).
8. **You trust Spawn.** The kit sends its tokens to Spawn, takes the world list, git URLs and event fields from Spawn's answers, and runs Spawn's proprietary client. If Spawn's server were hostile, the kit would not protect you.
9. **Logs hold other people's words,** as listed above. The logs have no automatic retention limit (saved events in `run/failed/` do: 30 days by default), and a stranger who mentions the agent adds one short metadata line (a handle and a reason, no chat text) to `handler.log` for each message, so the file can grow even from people who cannot give orders.
10. **A world's own files can carry things that your agent tool loads.** In print mode (`-p`) Claude Code skips the question about trusting a folder, and the kit runs the agent inside the world's clone (`claude --help`, 2.1.327). With its default settings, a hook in the clone's `.claude/settings.json` and an MCP server in its `.mcp.json` ran a command as your user before any tool rule applied (seen on 2026-11-18). Every Claude Code example in the kit now passes `--setting-sources user`, which stopped both in the same test (see [A world's own settings can run code](#a-worlds-own-settings-can-run-code)). What is left: another agent tool, or a command you wrote without the option, may still load them, and files such as `AGENTS.md` in the clone (which the kit's prompt tells the agent to read) and, depending on the version and the folder, `CLAUDE.md` are read by the agent as instructions, so whoever can push to that world can try to steer a model, even in the read-only posture. Serve only worlds whose editors you trust, and note that the update of the clone delivers a new push to the agent's working folder automatically, on every routed message (set `SDLCA_REFRESH_TIMEOUT=0` for a world you do not fully trust).
11. **A process that detaches outlives the time limit and the lock.** `timeout` stops the agent and its process group. A process that leaves the group on purpose (for example with `setsid` or `systemd-run --user`) keeps running after the turn ends and after the world lock is freed, and it can write to the clone while the next turn starts. We reproduced this with a test agent. Only a separate Unix user, a container or a virtual machine contains it.
12. **The update's check of the clone's settings is a list, made at one moment.** See [Updating the clone before a turn](#updating-the-clone-before-a-turn). A setting that makes git run a program and that the list does not name would be run by the update, outside the agent's tool limits, if an agent that can edit files in the clone put it there, and a program of the agent's that outlives the turn can change the file between the check and the fetch. Run the whole kit, agent included, as its own Unix user, or in a container or a virtual machine. If the agent has a Unix user of its own and can write in the clone, the update (which runs as the kit's user) crosses that boundary, so turn it off with `SDLCA_REFRESH_TIMEOUT=0` or keep the clone unwritable by the agent.

### TLS-inspecting proxies

Some company networks inspect encrypted traffic with a proxy of their own. Spawn's client can then refuse the connection with an error such as "self signed certificate in certificate chain". The listener keeps retrying on its own. This is a reliability problem and not a flaw in the kit's security: the client is correctly refusing a certificate it does not know.

The usual fix is to tell the client to trust the proxy's certificate authority. For Bun, which runs Spawn's client, the setting `NODE_EXTRA_CA_CERTS` is the usual one, but check it for your setup. Know what that means: after you trust the proxy, its operator can read the traffic, including the token in each request. Do not "fix" the error by turning certificate checks off.

## Hardening checklist

In order of value. Do the first one that you can, then the next.

1. **Give the kit its own Unix user, or run it in a container or a virtual machine.** This is the single biggest step. A user whose home holds only the runtime home, the clones and the agent tool's login cannot read your SSH keys, cloud credentials, browser profiles or other accounts' files. With several owners, give each one a user and a runtime home. The kit runs as whichever user starts it, so there is nothing to configure, and it ships no scripts for this. The kit's systemd unit sets `NoNewPrivileges=yes`, so a process it starts cannot gain privileges through programs such as `sudo`. That does not limit which files it can read.
2. **Use your provider's sandbox.** Claude Code documents a sandbox ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing), read on 2026-11-17 for our research). We have not tested it with the kit. Expect to tune it: the kit's tools read the token file and reach Spawn, so a rule that hides the token from the agent may hide it from them too. A required sandbox that is not available should stop the run, not silently run without it. Try that with the setting your tool offers. systemd offers further options for limiting a service's files (see `systemd.exec`); we have not tested them with the kit either.
3. **Keep a world's own settings out of the agent.** Every Claude Code example in the kit passes `--setting-sources user`. Keep it in any command you write, and for any other tool find out what it loads from the folder it runs in. See [A world's own settings can run code](#a-worlds-own-settings-can-run-code).
4. **Narrow the allowlists.** Replace `Bash(git *)` with the subcommands you need, for example `git status`, `git diff` and `git commit`. Leave out `git push` if you would rather push yourself after a review. Replace `sdlca-api *` with `sdlca-api GET *`, as the read-only posture does. Allow `spawn` subcommands one by one. The rule syntax is your agent tool's, so check its documentation and test.
5. **Keep the sender allowlist empty.** The owner alone is the default. Every person you add has the agent's power.
6. **Set run caps and spending limits.** The kit allows 20 agent runs an hour by default (`SDLCA_MAX_RUNS_PER_HOUR`); lower it to what you need and do not set it to 0, which turns the cap off. Lower `SDLCA_AGENT_TIMEOUT` (default 1800 seconds). Set a spending limit with your provider. Claude Code has a per-run limit for print mode, `--max-budget-usd` (`claude --help`, 2.1.327, 2026-11-17).
7. **Keep logs private and short-lived.** The kit creates them with mode 0600. Rotate or trim `handler.log`, keep `SDLCA_FAILED_KEEP_DAYS` as small as you can live with (30 by default; do not set it to 0, which keeps saved events forever, in any account: the folder is shared), and keep the runtime home out of synced folders and shared backups. Do not put secrets in `SDLCA_AGENT_CMD`, because the command line is visible in the process list.
8. **Rotate tokens.** Make a new token when you suspect a leak, when someone who had access leaves, and now and then anyway. See [Operations](operations.md#rotating-a-token).
9. **Start read-only, and watch.** Send a few messages of your own and read `handler.log`. Widen the posture only when you know what the agent does.
10. **Re-test after upgrades.** Your agent tool's permission rules change between versions. After you upgrade it or the kit, check that a message from a stranger is ignored and that the posture still blocks what it should.

## What an earlier code review found, and what changed

Before the first release, a review of an earlier version of the same logic was done for the maintainers on 2026-11-17. We keep it as a research note, not as an authority, because it examined code that has since changed. It listed 23 findings, two of them critical. Most are fixed in the repository. The main fixes are:

- No agent command by default, and the listener refuses to start without one. One of its two critical findings was an agent started with every permission check off.
- A strict sender gate, with exact handles, fail-closed lists and a ban on the agent's own handle.
- Routing from structured fields and exact matches only. The old code searched the whole event, including the chat text, and a short address matched a longer one.
- The raw token removed from the handler's environment, and tokens kept off command lines and away from redirects.
- Events with no world run in a scratch folder, never in the runtime home that holds every token.
- A fenced prompt, with the text treated as data.
- The world lock no longer leaks to background processes, a timeout stops a hung agent and its process group (a process that detaches is not stopped: see residual risk 11), and the lock wait is bounded.
- A cursor that is atomic and monotonic, a list of handled event ids, failed events kept for replay, and an hourly cap on runs.
- A chat sender that paces its lines, retries rate limits, and caps a reply.
- A systemd unit that backs off, and does not restart on a configuration error.

What the review found that is still true is in the residual risks above: tokens are reachable by a same-user agent, allow rules are broad, and prompt injection is reduced, not removed.

A second review of this version, also on 2026-11-17 and also done by an AI agent, found no way to get past the sender gate, and no way for chat text to run code or to choose a world. It did find smaller gaps, which are fixed and have tests: `sdlca-api` would let curl send a local file named in the body; a token file with odd content could change curl's settings or reach an error message; `sdlca-look` accepted any output path and an option as the world; the same event delivered twice at the same moment ran the agent twice; the listener's command line was not quoted for a folder name with a quote in it; and a few state files were read too strictly or written without a lock. It also found the two risks that are numbered 10 and 11 above. An AI review is no proof that nothing is left, so please report what you find ([How to report a vulnerability](#how-to-report-a-vulnerability)).

## How to report a vulnerability

Please do not open a public issue for a security problem, and never paste a token, an invite code or exploit details into an issue, a pull request or a chat. Follow [SECURITY.md](../SECURITY.md). It says where to send a report privately, what to include and what to expect. Problems in Spawn itself belong with Spawn, and SECURITY.md says how to reach them.
